# 文書テンプレートと状態の記録例

[文書の役割](document-roles.md) と [共通契約](workflow-contract.md) を併用してください。以下は記入用の例であり、実績ではありません。関係のない見出しを埋めるために機能・制約・確認を増やさず、既存プロジェクトの構成にも合わせてください。

## 使うテンプレート

- Patch: 目的・対象・維持条件・確認方法・実際の結果・未了・次の担当を直接引き渡す。正式なプラン一式は不要。
- Light: planと90、worklogは有効な場合だけ。
- Full: 10〜50、通常は60_review_packet、90。必要な場合だけ分割レビュー資料とworklog。
- 改訂: 要求・仕様を更新し、詳細は50またはLight notes、現在の採用と取り込み状態は90。

# Light Plan — 題名

## 目的・代表操作・成功結果

- 再現するもの / 省くもの:

## 範囲・対象外

## 要求と確認範囲
| ID | 要求・根拠 | 受け入れ条件 | 確認方法 | 証跡区分 |
| --- | --- | --- | --- | --- |
| REQ-01 | | | | |

- 今回確認する対象・期待結果:
- 方法・環境・観測:
- 今回の確認に含めない範囲:
- 直接確認できない条件: 理由、代替確認、残るリスク、判断条件
- 現在の結果と受け入れ: 90_status.mdを参照

## 実装方法と作業
- 対象箇所・構造・振る舞い・制約:
- 入力・成果・依存・統合・確認:
- 未確認の技術と調査・開始条件:

## Notes / Review / Amend
- 所見と対応、採否と理由、未決、改訂前後と影響:
```

## Full 10_claim.md / 20_app_requirement.md

10には目的、背景、当初の問題、対象者・環境、初期範囲、技術仮説、不確実性、次の文書への案内を置いてください。

20には目的、利用環境、代表入力・操作と成功結果、再現／省略範囲、最初に実現する機能、将来候補、今回の非目標を置いてください。決まっていない事項は仮説・未決として区別してください。

# Requirements

## 範囲と要求の根拠

## 機能要求
| ID | 要求・根拠 | 受け入れ条件 | 確認方法 | 証跡区分 |
| --- | --- | --- | --- | --- |
| REQ-01 | | | | |

## 非機能要求・制約・互換性
合意や適用制約に根拠のあるものだけを書く。追加がなければ「追加要求なし」。
改善を求められた場合は評価対象・合意した基準・条件を記録する。

## 検証範囲と完了条件
- 対象の機能・利用場面、期待結果:
- 確認する操作・コマンド・観測、必要な環境:
- Build / typecheck / unit / E2E等のうち今回含むものと対応REQ:
- 対象外とする確認:
- EXの場合の理由、代替確認、残るリスク、判断条件:
- 現在の証跡・判定: 90_status.md

## 対象外・未決
```

確認のレベル名だけを記入しないでください。対象外の検査は未達・pass・EXにせず、明示的な指示を引き継いでください。

## Full 40_specification.md と作業計画

40は全体事項（実装方針・採用理由、要求との対応のマップ、未確認と調査）を置き、肥大時は `42_spec(_req番号等)*.md` へreq単位・数reqまとめで設計詳細と手順の詳細を切り出してください（目安は40が約15kbに到達したとき）。WPは `41_work_packages.md` に置き、WPが無い規模のプランでは作らなくてよい。

```markdown
# Implementation Specification

## 実装方針・採用理由
確認済みの技術と根拠。候補・未確認・代替案は区別する。

必要なファイル構成、責務、データ、IF、状態、入力・出力、画面、

## 要求との対応
| REQ | 設計箇所 | 変更する成果 | 確認方法 |
| --- | --- | --- | --- |
| REQ-01 | | | |

## 作業計画（`41_work_packages.md` に置く。WPが無い規模のプランでは省略）
| WP | 目的・REQ | 入力・変更範囲 | 成果・完了条件 | 依存・開始条件 | 統合・確認 |
| --- | --- | --- | --- | --- | --- |
| WP-1 | | | | | |

- 問い・候補 / 観測対象 / 判断条件:
- 依存する作業と、その開始条件:
- 不成立時の代替案・必要な判断:

## 実施する確認
計画で決めた範囲の具体的な手順・コマンド・期待結果・環境を置く。
```

小さな仕事を管理目的だけで多くのWPへ分けないでください。調査WPの完了と、技術候補の実現性の確認を分けてください。

## Full 50_review_notes.md

レビュー所見、対応と根拠、未決・保留、見送った案と理由、現在の対象外、将来候補、文書反映、改訂履歴を置いてください。再計画要求と改訂返却はこのファイルへ追記し、現在の状態は90を参照してください。

所見には対象版・箇所、根拠となる要求、次の作業への影響、対応候補を付けてください。進められる範囲、阻害事項、未確認、`Suggest`（任意改善）を区別してください。指摘レベル（`Critical / Must-fix / Suggest`）はAcceptance判定とは別欄にしてください。

## 人が読むレビュー資料

60_review_packetは通常の入口です。利用者・操作・結果、範囲と制約、必要な判断、未確認と影響、正本の順に説明してください。初期概要の長さは目安で、重要な未決を隠す理由にしないでください。図は関係が分かりやすくなる場合に使い、枚数を要求にしないでください。

```markdown
# Review — 題名
対象版: 日付と内容を識別できる参照

## 利用者にとって何が変わるか
- 誰のどんな操作・結果が変わるか:
- 範囲 / 対象外 / 主要な制約:

## 判断事項
必要な判断、推奨案と理由、利用者への影響、受け入れる制約、意味のある代案。
判断が不要なら、その旨を書く。

## 未確認と影響
事実として未確認のこと、それが妨げる判断・作業、解消する条件。

## 根拠への入口
要求、仕様、調査、90への参照。経緯が必要なときだけ50・有効な91も示す。

## 今回の確認点
対象REQと未解決の前提に必要なものだけを選ぶ。
```

再レビューでは対象版の直後に変更・影響・再判断の有無を追記し、現在の全体像と未解決を維持してください。要約だけを書き換えて仕様の採用を確定しないでください。

分割が必要な場合は、60_review_briefをMarp形式の疎なスライド、70_review_boardを図と説明のHTML、80_review_checklistを関係する専門領域の確認項目として用意できます。画面・API・保存・環境等の無関係な領域を一律に必須化しないでください。外部CDN等の使用時は閲覧条件を明示してください。

読み手が次を把握できるかを確認してください。新しい承認ゲートや時間計測にはしません。

1. 誰のどんな結果が変わるか。
2. 何が範囲内・対象外か。
3. 推奨する方法、その理由と制約は何か。
4. 人が何を決めるか、または判断が不要か。
5. 何が未確認で、判断や実装へどう影響するか。

## 90_status.md — 唯一の進捗正本

90を作成・更新する前に、[文書の役割にある必須の更新契約](document-roles.md#90_statusmd--唯一の進捗正本)を読み、その更新タイミングと担当に従ってください。以下の記録形式を使い、作業進捗に応じて現在値を維持してください。

### 基本情報

先頭に既存の区分・状態・worklog選択を残してください。

```text
tier: Full
state: implementing
worklog: disabled
```

| state | 意味 |
| --- | --- |
| `planned` | 実装未着手。計画中か ready かは「現在の進行」で区別 |
| `implementing` | 実装中、または実装に関係する再計画・再開待ち |
| `accepting` | 実装結果の最終受け入れ・必要な完了処理を確認中 |
| `done` | 現行の全対象が pass または根拠付きの承認済みEXで、必要な完了処理も完了 |
| `abandoned` | 中止を決めた。理由と再検討条件を記録 |

一度の呼び出し終了、環境不足、再計画への引き渡しを `done` / `abandoned` にしないでください。影響する判定が未確認に戻れば `implementing` とし、旧判定は履歴に残してください。

### 現在の進行

| 項目 | 記録例 |
| --- | --- |
| 現在の工程 / 担当 | implement / Lv.2 implement |
| 担当leaderの実行参照 | 子agent起動結果の識別子、または単独実行の記録参照 |
| 呼び出し元 / 返却先 | Lv.1 process / Lv.1 process |
| 工程の結果 | `replan_required`。50のRP-001を参照 |
| 採用計画 | r1。内容を復元できるcommit・snapshot・保存資料等への参照 |
| 改訂案 | なし、またはr2と変更内容の参照 |
| 再計画要求 | RP-001 / 未処理。詳細は50 |
| 現在の作業 / 次の作業 | WP-2中断結果を保存済み / RP-001に限ってplanを実行 |
| 保留理由 / 再開条件 | 保存APIの制約を確定し、改訂をimplementで取り込む |

初回計画で実装への採用前なら、採用計画は「未採用」、利用可能な計画版と `ready` の報告参照を別途記録してください。計画版には記号だけでなく復元できる内容参照を添え、文書が書き換わった後も旧版との差を確認できるようにしてください。

再計画の状態は `未処理 → 計画中 → 返却済み → 取り込み中 → 取り込み済み` とし、依頼の詳細・改訂内容・以前の判定は50へ参照を張ってください。初版では一度に一つの再計画要求を扱い、状態を別の台帳へ分散しないでください。

### REQの実装・受け入れ

| ID | Requirement summary | Verification method | Evidence class | WP | Implementer state | Evidence | Acceptance |
| --- | --- | --- | --- | --- | --- | --- | --- |
| REQ-01 | 選択した項目を保存できる | 保存後の読み直し | E2 | WP-1/2 | in_progress | 対象版と操作結果への参照 | unverified: 必要な観測待ち |

`Implementer state` は `todo / in_progress / implemented / blocked` を維持してください。WP列は必要時に使ってください。`implemented` は実装報告であり、受け入れ済みではありません。

Acceptanceには `pass / fail / unverified / human-pending` と、判定者・対象版・根拠への参照を記録してください。EXは証跡区分です。承認された場合は `pass（EX承認、判断者・条件への参照）` のように、確認できた範囲と残るリスクを明示してください。

更新者は現在のLv.2 leaderです。専門役の実装・証跡報告を取り込み、独立したacceptanceまたは必要な人の判定を忠実に記録してください。leader自身の判断でpassを埋めないでください。

依頼した作業は「作業 / 参照REQ・WP / 担当役・子agent実行参照 / 状況 / 成果・次の条件」として記録してください。一件なら現在の進行欄で扱えますが、複数の作業は小さな表で追跡してください。計画中でREQ/WPがない場合は、対象文書や調査の問いで識別できます。起動失敗や未回収も記録し、実行参照を捏造しないでください。これはREQの受け入れ表とは区別してください。終了・取り下げ・置き換えた作業とREQには理由・後継を残し、取り下げを達成に数えず、REQ IDを別の意味へ再利用しないでください。

### 旧形式からの再開

既存のREQ・実装状態・証跡を保持し、分かる範囲で現在の進行を補ってください。ファイルが存在するだけでreadyや採用版を推定しないでください。対象版が不明なら何と照合すべきかを記録し、影響する作業の開始前に確認してください。91の不在を再開できない理由にしないでください。

## 再計画の記録例

詳細はFullの50、Lightのplan内notesへ書き、90は現在値とリンクだけを持ちます。以下は保存APIの制約が判明した場合の例です。

```text
RP-001: 保存完了の扱いを見直す
依頼者 / 返却先: implement / process
基準: 採用計画r1と復元用参照、実装snapshotと証跡参照
対象: REQ-01、40の保存API、WP-2
維持: 利用者が保存結果を読み直せること。他の機能・確認範囲は維持
理由: 実APIは非同期で、現在の設計では保存完了を観測できない
保存した成果: 呼び出し部分、実測結果、未完了の画面反映
稼働中の作業: 結果回収済み。同じ範囲を編集するworkerなし
planに求めるもの: 制約を踏まえたIF、失敗時の扱い、確認方法
再開条件: 改訂結果と影響をimplementが照合し、状態へ取り込む

RP-001への改訂返却
基準 / 改訂: r1 → r2。それぞれの復元用参照と差分
変更: 保存完了を待つIFと失敗時の通知。利用目的は維持
理由: 実APIの観測結果への参照
見直し指示: WP-2の待機処理、保存と読み直しのテスト、REQ-01の受け入れ
保持見込み: 入力処理。依存が変わらないかimplementで確認
未確認 / 範囲外への影響: 残件を具体的に記録。なければなし
結果: ready。改訂は返却済み・未取り込み
```

planが文書を改訂しても、実装の採用計画はimplementの取り込みが終わるまで旧版です。planは作業状態や旧受け入れを一括リセットしないでください。

implementは取り込み時に、保持・差分修正・追加・取り下げ・再確認を区別し、旧判定の対象版と根拠を履歴へ残してください。90の「取り込み中」から、採用版・作業・証跡・判定の整合を確認して「取り込み済み」へ更新し、その後workerを開始してください。途中終了した場合も、この未完了の取り込みを先に完了させてください。
