# 開発プロセス — 文書の役割と記録形式

[共通プロンプト](workflow-contract.md) と担当する役の本文に従い、必要な文書だけを読み書きしてください。この資料は既存の文書成果物を維持し、工程の切り替えと再開に必要な記録を補うためのものです。以下のパス・値・表の行は記入例であり、対象プロジェクトの実績ではありません。

## プロセス区分と保存場所

| 区分 | 適用する仕事 | 成果物 |
| --- | --- | --- |
| Patch | 新規依存・現行仕様の変更を伴わない局所的な修正・調査 | 正式なプラン一式は作らない。必要な確認結果、必要時の current docs / cheatsheet 更新 |
| Light | 仕様変更はあるが、新規依存・外部API・アーキテクチャ変更はない | プラン内の `plan.md` と `90_status.md` |
| Full | 新規依存・API・アーキテクチャ変更、広い影響、人による詳しいレビューがある | プラン内の10〜50、レビュー資料、90 |

既存プランでは選択済みの区分を継承してください。未選択なら必要な区分と理由を提示して利用者に確認し、回答済みの区分を繰り返し確認しないでください。「新規プロジェクト／追加要件／修正パッチ」という別の必須分類は追加しないでください。新規か既存変更かは、調査対象と要求の整理に反映してください。

既存プランの範囲内なら amend し、異なる目的・範囲なら新しいプランを作ってください。新規プランは `docs/plan_YYYYMMDD_<suffix>/` とし、日付と内容を表す短い snake_case を使ってください。連番だけの suffix を新設しないでください。既存ディレクトリの改名は必要な場合に別途扱い、命名の変更だけで作業を止めないでください。

検証や作業のために作る一時スクリプト・中間ファイルは、プロジェクトトップの `.planworks/` 以下に作成してください。`docs/` 以下に一時ファイルを作らないでください。一時ファイルは作業終了後に不要なら削除し、残す価値があるものはcheatsheetや成果物へ取り込んでください。

Light / Fullの区分と保存先が決まったら、plan leaderは専門作業を依頼する前にプランディレクトリと90を実際に作成してください。初回の90には`state: planned`、現在の工程・担当、計画中であること、判明している作業と次の依頼を記録します。未確定のREQや判定を埋める必要はありません。各計画文書は担当と保存先を指定して作成させ、leaderが実体と内容を確認してください。会話中の計画説明やファイル名の提示だけでは、計画文書を作成したことになりません。

既存プランでは90を読んで現在の進行を引き継いでください。90が欠けていれば、残された資料・成果・実行結果から確認できる内容を復元し、不明点を記録してから依頼を進めてください。文書作成を省くために、未確認の区分をPatchと決めつけたり、既存のLight / FullをPatchへ変更したりしてはなりません。

Patch の引き渡しには目的・対象・維持条件・確認方法・結果・未了・次の担当を直接記録できます。90を強制しないでください。仕様等の見直しが必要となり Patch を超える場合は、必要な Light / Full を確認し、保存先と引き渡し情報を整えてください。

実装修正を伴うPatchの最小チェーンは、implement leaderがdevelopへ実装と内部確認を委譲し、続いてacceptanceが独立判定する形です。tester・taskplanner・cheatsheetの起動やcheatsheetの新規作成は原則不要です。調査だけのPatchでは問いに必要な専門役へ依頼してください。調査によりPatchの前提を外れる変更が必要と分かった場合は、区分を再判定してください。新規依存・外部API・アーキテクチャ変更はFull、これらを伴わない現行仕様の変更はLightです。区分変更は利用者に確認してください。

## current docs とプラン索引

`docs/` 直下の現行文書は、確認済みの実装・運用に合わせてください。検討中の要求、未採用の設計、却下案、レビュー履歴はプラン内に置いてください。完了時は実装で確定した内容だけを現行文書へ取り込み、プラン一式をそのままコピーしないでください。

`docs/plan_index.md` はプランへの入口と状態の要約です。状態の正本は各プランの90であり、食い違えば索引を直してください。`completed`には90が`done`になった日付を`YYYY-MM-DD`で記入し、それ以外のstateでは`—`とします。Lv.1は工程返却時に90からstateとcompletedだけを転記し、tier・summary・notesは変更しません。

| plan | tier | summary | state | completed | notes |
| --- | --- | --- | --- | --- | --- |
| `plan_YYYYMMDD_data_export` | Full | データの書き出しを追加 | implementing | — | 再計画からの再開待ち。90を参照 |

## Full の文書

| 文書 | 残す内容 | 主な担当 |
| --- | --- | --- |
| `10_claim.md` | 要望、背景、対象者、当初の課題・仮説・不確実性 | requirement |
| `20_app_requirement.md` | 利用場面、代表入力・操作、成功時の結果、対象環境、範囲と省くもの | requirement |
| `30_requirement.md` | REQ、要求の根拠、受け入れ条件、確認方法、証跡区分、適用制約・対象外 | requirement、確認方法の助言は tester |
| `40_specification.md` | 構造・振る舞い・IF・エラー・変更箇所・採用理由の全体事項、各 `42_spec_*` へのマップ | architect |
| `41_work_packages.md` | WP、依存・実施手順。WP が無い規模のプランでは作らなくてよい | taskplanner |
| `42_spec(_req番号)*.md` | 40から切り出したreq単位・数reqまとめの設計詳細と手順。40が肥大したときに分割する | architect |
| `50_review_notes.md` | レビュー所見と対応、採否と理由、未解決、再計画要求・改訂差分・履歴 | reviewer、leader、指定された担当 |
| `60_review_packet.md` | 利用者が判断するための説明と正本への案内 | plan leader |
| `90_status.md` | 現在の工程、作業、実装・証跡・受け入れ | 現在の Lv.2 leader |

文書間で同じ詳細を複製せず、REQ・仕様・証跡への参照を使ってください。10には当初の要望を残し、現在の範囲は20/30、現在の設計は40、変更理由は50で分かるようにしてください。

30の記入単位は次のとおりです。非機能の追加要求がなければ、その旨を記録し、欄を埋めるための目標を作らないでください。

| ID | 要求・根拠 | 受け入れ条件 | 確認方法 / 証跡区分 |
| --- | --- | --- | --- |
| REQ-01 | 利用者が選んだ項目を保存できる。根拠: 対象の利用場面 | 合意した入力が保存され、読み直した結果が一致する | 指定操作で保存後に読み直し、値を比較 / E2 |

検証範囲には、今回の対象・期待結果・方法・対象外を記録してください。要件に関係する場合は、正常系に加えてエラー時・境界値・不正入力を確認範囲に含めるかも明記してください。すべての仕事で一律に必須化せず、E2E・回帰・性能評価なども今回含むかを明確にし、レベル名による定型セットにしないでください。直接確認できない条件は、EXの理由・代替確認・残るリスク・判断条件を記録してください。

40は対象に必要な設計項目だけを書いてください。画面のない仕事に画面設計、データを扱わない仕事にDB設計を作る必要はありません。採用技術の確認済み能力と、未確認の候補・代替案を区別してください。40が肥大して見通しが悪くなったときは、req単位または数reqまとめで `42_spec(_req番号等)*.md` へ設計詳細と手順の詳細を切り出してください。分割の判断は40が約15kbに到達したときを目安にし、40には全体事項と各 `42_spec_*` へのマップを残してください。

WP は `41_work_packages.md` に書いてください。WP が無い規模のプランでは作らなくてよい。WP は次の情報を持たせてください。単なるファイル別の分割ではなく、必要な入力と成果、完了の確認が分かる単位にします。WP は作業計画であり、その完了報告だけで REQ の pass にはなりません。

| WP | 目的・対応REQ | 入力・対象箇所 | 成果・完了条件 | 依存・統合・確認 |
| --- | --- | --- | --- | --- |
| WP-1 | 保存方法を確認 / REQ-01 | 外部仕様、隔離した試作用データ | 保存と読み直しの可否・制約を観測して報告 | 成功条件を満たした場合にのみ依存WPを開始 |

調査WPには問い、観測対象、判断条件、依存作業の開始条件を書いてください。計画を作ったことを技術検証の成功としないでください。

## Light の文書

`plan.md` に、目的・代表操作と成功結果、範囲／対象外、要求と受け入れ条件、変更方法と確認手順、所見・変更履歴をまとめてください。90へのリンクを付け、状態の正本は90に保ってください。

初期の説明は1〜2画面程度を目安にし、内容を無理に圧縮して重要な条件を失わないでください。内容が広がるか、依存・API・構造の変更を含む場合は Full への移行を検討してください。Light のためだけの別の要約文書は不要です。

## 人が読むレビュー資料

Full は通常 `60_review_packet.md` を使ってください。最初に、誰のどんな操作・結果が変わるか、現在の範囲・対象外・主要な制約を簡潔に説明してください。続いて判断事項、未確認と影響、正本へのリンク、今回固有の確認点を置いてください。

判断事項には推奨案・理由・利用者への影響・意味のある代案を添えてください。新たな判断が不要ならそう記載してください。再レビューでは変更・影響・再判断の有無を先に示し、現在の全体像と未解決事項を残してください。記録を読まないと現在の結論が分からない資料にしないでください。

複数担当のレビューを分ける必要があるときは、既存の分割形式も使えます。

- `60_review_brief.md`: Marp形式の入口。全体像から判断・根拠へ案内する。
- `70_review_board.html`: 図で関係・振る舞いを説明する資料。必要な場合だけ作る。
- `80_review_checklist.md`: 関連する専門領域ごとの確認項目。全領域を一律に必須化しない。

分割しても判断の正本を増やさないでください。図やスライドの枚数を完成条件にしないでください。

## cheatsheet

`docs/cheatsheet/` は、繰り返し調べずに利用できる知識・実測結果の置き場所です。プロジェクトの製品要求・設計の採否・時系列の作業履歴はプランへ残してください。

| ファイル | 記録する内容 |
| --- | --- |
| `index.md` | トピック、対象技術・版、確認日、知識の種類、読む場面、本文へのリンク |
| `link.md` | 外部の出典URL、出典種別、確認日、関連ローカル資料、参照理由 |
| `domain_primer.md` | 必要な場合に、対象領域の目的・道具・登場者・行為・用語・成立条件・誤解しやすい点 |
| トピック別本文 | 必要な知識、利用条件、実行結果、制約、代替案、未確認、再確認条件 |

Web由来の情報は一次資料を優先し、出典をlinkへ残してください。ローカル検証は架空のURLを作らず、確認日・対象版・環境・コマンドまたは操作・期待と実際・失敗条件を本文へ残してください。古い知識は対象版と条件が一致するか確認して使ってください。

既存の調査結果を再利用するときは、判断に関係するパッケージ・APIの版、ランタイム、OS・環境、設定・権限と観測条件を比較し、記録結果が今回にも適用できる根拠を示してください。関係する条件が一致し、影響する変更がなければ再調査を省けます。依存のmajor / minor更新、API・ランタイム・実行環境の差、deprecated警告などは影響する能力を再確認するトリガーです。差が無関係な結果まで一律に無効化せず、再確認範囲を限定してください。

採用判断に使うライブラリやAPIは、採用理由に挙げた能力ごとに最小のコード・型・呼び出し・操作で確認してください。importや起動だけでは、別の機能や利用結果が得られることまで証明しません。結果を観測できる手段も確認してください。

未確認の能力が残る候補は条件付き・未解決のままとし、Go / No-Go の判断条件と依存作業の開始条件を記録してください。認証等で実行できない場合は理由・代替確認・リスク・必要な判断を残してください。秘密情報は保存せず、環境変数名や必要な権限だけを記載してください。

## 90_status.md — 唯一の進捗正本

**Light / Fullのプロジェクト遂行は90に記録した現在の進行に従い、作業進捗に応じて90を更新してください。90の作成・参照・継続更新は必須の実行契約です。**

90から要求・仕様・証跡の正本を参照してください。90に書かれた要約だけで要求や受け入れ条件を置き換えないでください。新しい利用者指示や実際の成果と食い違う場合は、その根拠と影響を確認し、担当権限の範囲で記録を更新してください。

### 必須の更新タイミング

| タイミング | 現在のLv.2 leaderが行うこと |
| --- | --- |
| 開始・再開 | 90を読み、採用版・改訂状態・担当・未了・開始条件を実際の成果と照合する。現在の工程と次の作業を更新する |
| 子agentへの依頼 | 対象作業・対応REQ/WP・担当役・開始条件を記録する。起動前は依頼予定とし、起動成功後に実行参照と実行中の状態を記録する |
| 結果の回収 | 成果物・対象版・確認結果・未達を照合し、作業状態と根拠への参照を更新する。その後に後続作業を決める |
| レビュー・受け入れ結果の取得 | 所見・対応先・残件を反映する。Acceptance列は独立した判定報告を根拠に更新する |
| 失敗・中断・判断待ち | 完了した範囲、未回収の担当、未了、保留理由、再開条件を記録する。未実施を完了にしない |
| 再計画・改訂取り込み | 要求ID、採用版と改訂案、取り込み状態、影響する作業・判定を更新する |
| 工程返却・終了 | 工程の結果、保存先、未了、次の担当・作業を更新し、返却報告と一致していることを確認する |

変化のない待機や個々のファイル読み取りまで記録する必要はありません。作業状態・担当・成果・判断・次の条件が変わった時点で更新してください。Lv.2は呼び出しを返す前に次の担当・作業・再開条件まで記録して更新を終えます。Lv.1は内容を照合し、次のLv.2に読み直させてください。Lv.3は90への更新材料を返します。

更新が失敗した場合は、実行中作業の安全な回収・中断と記録の復旧を優先し、記録が整うまで後続の新規作業へ進まないでください。保存できない場合は、保存済みの場所、保存できなかった内容、復旧に必要な条件を返してください。90の未更新を隠して`ready` / `complete`を返してはなりません。

### 基本情報

先頭に既存の区分・状態・worklog選択を残してください。

```text
tier: Full
state: implementing
worklog: disabled
```

| state | 意味 |
| --- | --- |
| `planned` | 実装未着手。計画中か ready かは「現在の進行」で区別 |
| `implementing` | 実装中、または実装に関係する再計画・再開待ち |
| `accepting` | 実装結果の最終受け入れ・必要な完了処理を確認中 |
| `done` | 現行の全対象が pass または根拠付きの承認済みEXで、必要な完了処理も完了 |
| `abandoned` | 中止を決めた。理由と再検討条件を記録 |

一度の呼び出し終了、環境不足、再計画への引き渡しを `done` / `abandoned` にしないでください。影響する判定が未確認に戻れば `implementing` とし、旧判定は履歴に残してください。

### 現在の進行

| 項目 | 記録例 |
| --- | --- |
| 現在の工程 / 担当 | implement / Lv.2 implement |
| 担当leaderの実行参照 | 子agent起動結果の識別子、または単独実行の記録参照 |
| 呼び出し元 / 返却先 | Lv.1 process / Lv.1 process |
| 工程の結果 | `replan_required`。50のRP-001を参照 |
| 採用計画 | r1。内容を復元できるcommit・snapshot・保存資料等への参照 |
| 改訂案 | なし、またはr2と変更内容の参照 |
| 再計画要求 | RP-001 / 未処理。詳細は50 |
| 現在の作業 / 次の作業 | WP-2中断結果を保存済み / RP-001に限ってplanを実行 |
| 保留理由 / 再開条件 | 保存APIの制約を確定し、改訂をimplementで取り込む |

初回計画で実装への採用前なら、採用計画は「未採用」、利用可能な計画版と `ready` の報告参照を別途記録してください。計画版には記号だけでなく復元できる内容参照を添え、文書が書き換わった後も旧版との差を確認できるようにしてください。

再計画の状態は `未処理 → 計画中 → 返却済み → 取り込み中 → 取り込み済み` とし、依頼の詳細・改訂内容・以前の判定は50へ参照を張ってください。初版では一度に一つの再計画要求を扱い、状態を別の台帳へ分散しないでください。

### REQの実装・受け入れ

| ID | Requirement summary | 対象設計ID | 状態 | Verification method | Evidence class | WP | Implementer state | Evidence | Acceptance |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| REQ-01 | 選択した項目を保存できる | D-001 | 今回実装 | 保存後の読み直し | E2 | WP-1/2 | in_progress | 対象版と操作結果への参照 | unverified: 必要な観測待ち |

`状態` 列は `今回実装 / 後続移管 / 対象外 / 未確定` で範囲を仕分けます（ready では未確定のまま流さず確定すること）。`Implementer state` は `todo / in_progress / implemented / blocked` を維持してください。WP列は必要時に使ってください。`implemented` は実装報告であり、受け入れ済みではありません。ここでの `blocked` は特定REQの実装作業が進められない状態であり、工程の返却結果としての `blocked` や `Acceptance` の `unverified` とは別の語です。3つの語の区別は[共通プロンプトの状態語彙の区別](workflow-contract.md)を参照してください。

Acceptanceには `pass / fail / unverified / human-pending` と、判定者・対象版・根拠への参照を記録してください。状態が `対象外` または `後続移管` の行には判定を入れず、空欄または `-` としてください。EXは証跡区分です。承認された場合は `pass（EX承認、判断者・条件への参照）` のように、確認できた範囲と残るリスクを明示してください。

### 環境宣言

同梱の任意ツールを使う場合だけ、[成果版・fixture同一性確認ツール](artifact-identity.md)を参照できます。`snapshot`でファイル一覧と機械IDをJSONへ記録し、`verify`で独立に照合します。宣言の本文や試験結果は書き換えません。

各担当が同じ成果版（artifact）とテスト資産・fixtureを指し、その同一性を確認するための宣言です。**対象の特定・照合は必須ですが、ID生成スクリプトの利用は任意です。** Pythonや特定のスクリプトを基本スキルの実行条件にせず、実行agentが環境と必要性に応じて手段を選んでください。スクリプトを使わない場合も、利用可能な版参照や対象ファイルの内容による照合を行い、確認できた範囲と限界を記録してください。

Light / Full の計画時（`ready`）に、1計画1ファイルの `docs/plan_YYYYMMDD_*/env_manifest.md` を作り、受け入れ時（`complete`）には受け入れ対象版と証跡に対応する情報へ更新してください。`90_status.md` にはそのファイルパス1行だけを記録し、本文を転記して二重台帳にしないでください。Patchでは引き渡し記録に対象ソース版・成果物とテスト資産の2行に簡略化できます。宣言がない計画は `ready` にしませんが、スクリプトの不使用や機械IDの未取得だけを理由に止めないでください。

```markdown
### 環境宣言（Environment Manifest）

1. **実行環境（自己申告）**: `Windows 11 / PowerShell` 等。実際に使用した環境を記録する
2. **対象ソース版・成果物**:
   - 対象参照: `<commit / snapshot / 保存した成果物・差分への参照 / 内容ハッシュ等>`
   - 対象範囲: `<リポジトリルート等の起点＋対象ファイル一覧または集合定義>`
   - 特定・照合方法: `<VCS参照と未コミット差分の確認 / 保存物の内容比較 / 任意のID生成スクリプト等>`
3. **テスト資産・fixture**:
   - 対象範囲: `<起点＋ファイル一覧またはglob等の集合定義>`
   - 期待件数・出所 / 確認件数: `<件数で照合する場合に記録>`
   - 対象参照: `<版に固定した資産への参照 / 保存した資産一式 / 内容ハッシュ等>`
   - 特記事項: 故障注入モック・専用環境変数の分離状況。対象資産がない場合はその理由
4. **採取・突合手段と結果**:
   - 使用手段: `<手動確認 / VCS・標準ツール / 任意スクリプト名＋版等>`
   - 機械IDを使う場合: `<方式名・起点・集合定義・ハッシュ等、独立再採取に必要な情報>`
   - 機械IDを使わない場合: `<代替の参照・内容比較方法と、機械IDを取得しない理由>`
   - 照合結果: `<実際に比較した項目と一致 / 不一致。未照合の項目と理由>`
5. **変更履歴（ready以降）**:
   - 日時 / 変更項目 / 理由 / 再確認範囲 / 影響を受ける試験結果
```

スクリプトを使わない記録例: 「対象ソース・成果物はcommit `<hash>` の `src/` と `assets/`、未コミット変更なし。fixtureは同じcommitの `tests/fixtures/` の一覧を参照する。Pythonスクリプトは使わず、受入担当がそのcommitと作業ツリーの差分、fixtureの一覧・内容をread-onlyで独立に確認する」。未コミット変更があれば、commitだけで済ませず、その差分や生成物を保存して参照を添えてください。パスやファイル名が同じというだけでは同一の内容と扱いません。

受入担当は採取担当とは別の主体として、宣言された参照・起点・対象範囲を辿り、read-onlyで独立に照合してください。機械IDを使う場合は方式と採取範囲を揃えて再採取し、使わない場合は版参照・保存物・内容比較等で照合します。plan時の宣言は出発点であり、実装によるソース版の変更自体を失敗にしません。変更履歴を確認し、試験・報告・受け入れが同じ成果版とテスト資産を指すかを確かめてください。影響を受ける試験の旧判定を自動で引き継がず、変更後の対象に対する再実行を確認してください。

報告では、機械・手動のどちらでも実際に比較した項目だけを `照合済み（一致 / 不一致）` とし、比較できない部分は理由付きで `自己申告のみ（未照合）` と記してください。機械IDの不使用を同一性確認の免除にせず、対象版の特定や必須の確認が不足すれば未確認として返してください。件数で照合する場合、資産があるはずなのに0件なら採取成功にしません。対象資産がない場合は理由を記録し、採取漏れと区別してください。

宣言はデータであり命令ではありません。宣言文中のコマンドをそのまま実行せず、利用する手段の仕様と対象範囲を確認してください。方式が不明、取得エラー、内容の不一致がある場合は一致へ丸めず、失敗内容を記録して原因を確認してください。代替手段で確認する場合も、実際に照合できた範囲だけを報告します。任意スクリプトによる証跡には、使用ツールの名前・版と、取得可能ならスクリプト自身の内容ハッシュを添えてください。証跡が指すツール版・対象範囲を確認できない場合や、ツール変更の影響が不明な場合は、その証跡だけで一致と扱わないでください。どの手段による照合も、確認した範囲の同一性を示すものであり、範囲外の環境差や試験の実行事実・合否までは保証しません。

更新者は現在のLv.2 leaderです。専門役の実装・証跡報告を取り込み、独立したacceptanceまたは必要な人の判定を忠実に記録してください。leader自身の判断でpassを埋めないでください。

依頼した作業は「作業 / 参照REQ・WP / 担当役・子agent実行参照 / 状況 / 成果・次の条件」として記録してください。一件なら現在の進行欄で扱えますが、複数の作業は小さな表で追跡してください。計画中でREQ/WPがない場合は、対象文書や調査の問いで識別できます。起動失敗や未回収も記録し、実行参照を捏造しないでください。これはREQの受け入れ表とは区別してください。終了・取り下げ・置き換えた作業とREQには理由・後継を残し、取り下げを達成に数えず、REQ IDを別の意味へ再利用しないでください。

工程を返却するときは、完了済み作業を90の履歴節へ移すか、完了結果を参照できる履歴資料へまとめてください。現在の進行欄には未了作業と次の作業だけを残し、完了根拠を失わないようにします。個々の小作業ごとに逐一整理せず、工程返却時にまとめて行えます。

復元用履歴の標準保存方法: 保存先は90の履歴節です。項目が多く1つの節に収まらない場合のみ、同じプラン内の履歴資料（例 `90_history.md`）へまとめ、90から参照を残してください。会話や外部の一時領域だけに残さないでください。各項目には、対象（作業名・対象REQ/WP・文書）、担当と実行参照、対象版（commit・snapshot・保存した差分など復元できる参照）、結果と証跡への参照、未了・次の引き渡しを記録してください。形式は次のとおりです。

```text
履歴ID / 対象（作業・REQ/WP・文書）:
担当 / 実行参照 / 対象版:
結果 / 証跡への参照:
未了・次の引き渡し:
```

### 旧形式からの再開

既存のREQ・実装状態・証跡を保持し、分かる範囲で現在の進行を補ってください。ファイルが存在するだけでreadyや採用版を推定しないでください。対象版が不明なら何と照合すべきかを記録し、影響する作業の開始前に確認してください。91の不在を再開できない理由にしないでください。

## 再計画の記録例

詳細はFullの50、Lightのplan内notesへ書き、90は現在値とリンクだけを持ちます。以下は保存APIの制約が判明した場合の例です。

```text
RP-001: 保存完了の扱いを見直す
依頼者 / 返却先: implement / process
基準: 採用計画r1と復元用参照、実装snapshotと証跡参照
対象: REQ-01、40の保存API、WP-2
維持: 利用者が保存結果を読み直せること。他の機能・確認範囲は維持
理由: 実APIは非同期で、現在の設計では保存完了を観測できない
保存した成果: 呼び出し部分、実測結果、未完了の画面反映
稼働中の作業: 結果回収済み。同じ範囲を編集するworkerなし
planに求めるもの: 制約を踏まえたIF、失敗時の扱い、確認方法
再開条件: 改訂結果と影響をimplementが照合し、状態へ取り込む

RP-001への改訂返却
基準 / 改訂: r1 → r2。それぞれの復元用参照と差分
変更: 保存完了を待つIFと失敗時の通知。利用目的は維持
理由: 実APIの観測結果への参照
見直し指示: WP-2の待機処理、保存と読み直しのテスト、REQ-01の受け入れ
保持見込み: 入力処理。依存が変わらないかimplementで確認
未確認 / 範囲外への影響: 残件を具体的に記録。なければなし
結果: ready。改訂は返却済み・未取り込み
```

planが文書を改訂しても、実装の採用計画はimplementの取り込みが終わるまで旧版です。planは作業状態や旧受け入れを一括リセットしないでください。

implementは取り込み時に、保持・差分修正・追加・取り下げ・再確認を区別し、旧判定の対象版と根拠を履歴へ残してください。90の「取り込み中」から、採用版・作業・証跡・判定の整合を確認して「取り込み済み」へ更新し、その後workerを開始してください。途中終了した場合も、この未完了の取り込みを先に完了させてください。

## 91_worklog.md — 任意の判断経緯

新規Light / Fullでは `91_worklog.md` を既定で作成せず、90へ `worklog: disabled` と記録してください。判断経緯を別途追跡する必要がある場合、利用者が希望した場合、または既存計画の設定を継承する場合に限って `enabled` とし、90へ選択を記録します。既存の回答を継承してください。無効なら91を作らず、判断は50またはLightのnotesへ残してください。

有効なら、意味のある調査・要求整理・設計・レビュー・実装・受け入れ・文書反映ごとに、日時、対象、入力、行ったこと、根拠、決定・未決、成果物への参照を簡潔に残してください。新構成では固定された旧工程番号の消化を求めないでください。

実装・デバッグの記録は、`症状 → 仮説 → 修正 → 確認` の4行を基本に簡潔に残してください。help要請（症状 / 試したこと / 疑っている外的要因 / 無効になった資産の4行と再現コマンドへの参照）も同じ形式で残します。協議を経て方針を変えた場合は「方針転換」の1行（決めた方針・理由）を追記してください。デバッグの試行の全ログは残さないでください。1回目の失敗時点の1行の状況報告は、4行証跡とも help の4行とも別枠の任意の記録として残してください。help として数えないでください。

会話全文、長い実行ログ、秘密情報、要求や状態の複製は入れないでください。91は経緯を読む補助資料で、90や要求・仕様の正本に代わるものではありません。`92_replan.md` は初版では作らず、将来詳細を分けても現在の状態は90に保ってください。
